# mpegmech 概要设计

> 版本 v0.1（草案） · 2026-10-31
> 状态：**待评审** —— 接口定型，实现未开始

---

## 1. 定位

### 1.1 一句话

mpegmech 是一个 **PS/TS 容器层**的封装与解封装库，核心差异点是
**输入容许任意切分**：`feed()` 喂进来多少都行，不需要 188 字节对齐、不需要落在
PES 边界、也不需要是完整的一帧。

### 1.2 与现有实现的差异

| | libmpeg | ffmpeg (libavformat) | **mpegmech** |
|---|---|---|---|
| 输入切分 | PS 容忍任意切分；**TS 强制 188 字节 + 首字节 0x47**（`assert`，Release 下失效后静默错位） | 内部 AVIO 缓冲，容忍任意切分 | **两者都容忍任意切分** |
| 中途接入 | PS 靠搜索 `00 00 01 BA` 自同步；TS 不做同步搜索 | 有 probe 逻辑，可自同步 | 都有：TS 走 0x47 多重校验，PS 走 startcode |
| 失步恢复 | 无（TS 一旦错位就一直错） | 有 | 有，且计入 `resyncs` 统计 |
| 依赖体积 | 无外部依赖 | 大（avformat + avcodec + swscale…） | 无外部依赖，仅标准库 |
| 输出缓冲责任 | **调用方**保存"消费不掉的尾巴" | 内部 | **内部**（`feed()` 全部消费） |
| 语言/ABI | C | C | C++17（pimpl 隔离实现） |

### 1.3 不做什么（明确的边界）

| 不做 | 原因 |
|---|---|
| **解码 / 编码** | 只做容器层。ES 交出去是压缩码流，交给下游解码器 |
| **RTP 打包 / 抖动缓冲 / 重排** | 那是 `rtpmech` 的职责，两者通过 ES 帧对接 |
| **RTSP / HTTP 信令** | 传输层之上，不属于本库 |
| **转码 / 分辨率变换** | 同上 |
| **ADTS 长度解析**（AAC 的帧长） | H.26x 的 AnnexB 拆帧由 `EsSplitter` 做（见 §5.9）。AAC 的 ADTS 拆帧**仅在 demux 的 TS 路径做**（见 §5.12）：一条 PES 里常见的多帧 ADTS 会被拆成单帧；封装侧仍要求调用方按帧给 |
| **PS/TS 之间的互转** | 可以由 demux → mux 组合完成，不单独提供 |

## 2. 适用范围

### 2.1 容器

| 容器 | 封装 | 解封装 | 备注 |
|---|---|---|---|
| MPEG-2 PS（ISO/IEC 13818-1 系统层） | ✅ | ✅ | 含 MPEG-1 兼容流的读取 |
| MPEG-2 TS | ✅ | ✅ | 单节目；多节目读取支持，多节目封装 v1 不做 |

### 2.2 编码

| 类别 | 支持 |
|---|---|
| 视频 | H.264 / H.265 / H.266 / MPEG-4 / MPEG-2 / MPEG-1 / SVAC / AVS3 |
| 音频 | AAC / MP3 / AC3 / EAC3 / G.711A / G.711U / G.722 / G.723 / G.729 / OPUS / SVAC |

> v1 实现优先级：**H.264 + H.265 + AAC + G.711A/U**。
> 其余枚举值先占位，遇到未实现的 codec 返回 `unsupported_codec`，
> 而不是静默丢弃 —— 宁可报错，不要"看起来正常但没有数据"。

### 2.3 部署形态

- 目标平台：Windows x64（开发）、Linux aarch64（板端，交叉编译 `aarch64-none-linux-gnu-`）
- 体积目标：`.so` < 300 KB（无外部依赖，纯 C++17 标准库）
- 无异常依赖：可预期失败一律 `std::error_code`

### 3.3 依赖

**零外部依赖**。仅 C++17 标准库（`<vector>` `<cstdint>` `<functional>` `<system_error>`）。

刻意不依赖 `rtpmech` / `netmech`：容器处理与网络栈没有耦合理由，
硬绑在一起会让库无法单独用于文件转封装场景。

## 4. 对外接口

### 4.1 概括

```cpp
// 解封装：容器流 -> ES 帧
auto dx = Demuxer::create(cfg, onFrame, onStream, ec);
dx->feed(chunk);      // chunk 长度随意
dx->flush();

// 封装：ES 帧 -> 容器流
auto mx = Muxer::create(cfg, onOutput, ec);
mx->addStream(sc, sid);
mx->write(sid, FrameFlag::key, pts, dts, frame);
mx->flush();
```

### 4.2 Demuxer

| 接口 | 语义 |
|---|---|
| `static create(cfg, on_frame, on_stream, ec)` | 工厂。回调可为空？`on_frame` **必填**，`on_stream` 可空 |
| `feed(span<const uint8_t>)` | **全部消费**。返回 `std::error_code`，不返回消费字节数 |
| `flush()` | 输入结束，处理内部残余 |
| `reset()` | 清空缓冲与状态，可复用于新流 |
| `container()` | 已识别的容器（嗅探完成前为 `unknown`） |
| `buffered()` | 内部暂存字节数（水位观测） |
| `stats()` | `DemuxStats` 快照 |

**回调契约**（写进头文件，实现必须遵守）：

1. 在 `feed()` / `flush()` 栈内**同步**执行，串行、不并发；
2. 回调里不得调用本对象的 `feed` / `flush` / `reset`；
3. `payload` 指向库内缓冲，**回调返回后失效**；
4. 回调抛异常会穿过 `feed()` 传播，库内不捕获。

`feed` 为什么"全部消费"而不是像 libmpeg 那样返回 consume 字节数：
**把"存尾巴"这件事从调用方手里收回来**。libmpeg 的契约要求调用方
`memcpy(NEXTBUFFER, data + n, bytes - n)`，一旦漏写或写错，流就永久错位，
而且没有任何报错 —— 这是本库要消灭的一类缺陷。

### 4.3 Muxer

| 接口 | 语义 |
|---|---|
| `static create(cfg, on_output, ec)` | 工厂。`container` 必须是 ps 或 ts |
| `addStream(cfg, sid)` | 登记 ES 流，分配 PID / stream_id |
| `write(sid, flags, pts, dts, es)` | 写入**一整帧** |
| `flush()` | 冲刷最后一个包 / pack |
| `stats()` / `streamCount()` | 统计 |

**输出契约**：每次回调交出的字节**可直接发送** —— TS 是 188 的整数倍，
PS 是一个完整 pack（pack_header + 若干 PES）。调用方不需要再攒。

### 4.4 EsSplitter（ES 切帧器）

**为什么单独一个类，不塞进 Muxer**：

切帧和封装是两件事。塞在一起会让"时间戳怎么给"变糊——一次 `feed` 可能跨
好几帧，调用方没法给每帧一个 pts。分开之后，切出来的每一帧都过一次回调，
调用方在那里按自己的节奏推进时间戳（真实采集场景本来就知道每帧什么时候到）。

```cpp
mpegmech::EsSplitter::Config sc;
sc.codec            = VideoCodec::h264;
sc.max_frame_bytes  = 1024 * 1024;

auto splitter = EsSplitter::create(sc, ec);

std::int64_t pts = 0;
splitter->feed(socket_buf, [&](span<const uint8_t> frame) {
    muxer->write(sid, FrameFlag::key, pts, pts, frame);
    pts += 3600;                       // 90kHz / 25fps
});
```

| 接口 | 说明 |
|---|---|
| `feed(data, on_frame)` | 喂任意切片，每切出一帧回调一次 |
| `flush(on_frame)` | 流结束时交出最后一帧 |
| `reset()` | 换流时清状态 |

**帧边界判断**：有 AUD 时按 AUD 切（H.264 type 9 / H.265 type 35）；没有 AUD
时按"下一个 VCL NAL 且 `first_mb_in_slice == 0`"切。

### 4.5 错误与统计

错误码见 `error.hpp`，分三档：

| 档 | 错误 | 调用方处置 |
|---|---|---|
| 可恢复（库已自行处理） | `buffer_overflow` / `sync_lost` | 记录日志，`sync_lost` 需 `reset()` |
| 输入非法（属 bug） | `invalid_argument` / `malformed` | 修调用方代码 |
| 环境不符 | `unsupported_container` / `unsupported_codec` | 换配置或不支持该码流 |

统计字段设计原则：**能定位问题的最小集合**。`bytes_skipped` / `resyncs` /
`parse_errors` 三个数就能区分"流本身脏"和"实现有 bug"：

- `bytes_skipped` 只在启动和中途失步时增长，稳态下不该动；
- `resyncs` 稳态下应该恒为 0，一旦在涨说明链路在丢数据；
- `parse_errors` 在涨说明码流不符合规范（或实现漏了分支）。

## 5. 关键设计

### 5.1 非整帧输入：缓冲 + 同步状态机

这是整个库的核心。一个 `ByteQueue` + 一个两态机：

```
        ┌──────────────┐   找到同步点    ┌──────────────┐
        │   SEARCHING  │ ──────────────► │   SYNCED     │
        │  (丢弃字节)   │                 │  (正常解析)   │
        └──────────────┘ ◄────────────── └──────────────┘
               ▲          包边界不符 / 解析异常
               │
               │  失步累计 > ts_max_resync_bytes
               └──────────► 返回 sync_lost
```

**为什么不用"到达即解析"**：一个 TS 包 188 字节，`recv()` 回来 100 字节时
既不是包也不是包的一部分边界，只能等。等待就意味着暂存，暂存的极值必须有上限，
上限触发必须有明确策略 —— 这三件事都要设计，不能让它们"自然发生"。

**ByteQueue 的形态**：连续内存 `std::vector<uint8_t>` + 读游标，而不是真环形缓冲。

| | 环形 | 连续 + 游标 |
|---|---|---|
| 实现复杂度 | 高（回绕分支遍布解析代码） | 低 |
| PES 组装 | 要处理跨回绕 | 直接 `span` |
| 扩容 | 需搬移或重建 | `memmove` 压缩 |
| 峰值内存 | 固定 | 固定（压缩后稳定在 `max_buffered_bytes` 内） |

选**连续 + 游标**：解析代码里到处都是 `data[i]`，回绕分支会把代码写成两倍。
压缩时机：读游标超过容量一半时 `memmove` 未消费部分到头部。

**溢出策略**：达到 `max_buffered_bytes` 时

1. 丢弃读游标之前的全部已消费数据（本来就该回收）；
2. 仍然溢出（说明积压的是未成帧数据）→ 丢弃**最旧的一半**，回到 SEARCHING，
   `overflow_drops++`，返回 `buffer_overflow`。

丢最旧而不是丢最新：最新数据里才有同步点；丢中间会破坏剩余数据的连续性。

### 5.2 TS 同步算法

```
在 buffer 中找最小的 k，使：
    buf[k]            == 0x47
    buf[k + 188]      == 0x47
    buf[k + 2*188]    == 0x47        (连续包数 ts_sync_packets，默认 3)
```

**为什么是 3 个而不是 1 个**：0x47 是普通字节值，在压缩数据里出现频率约 1/256。
只校验 1 个，随机数据在 188 字节窗口内几乎必然命中，会造成"看起来同步了、
其实全是垃圾"的假同步。校验 2 个后误判率降到约 1/65536，3 个后约 1/16.7M
（对随机数据），且真实 TS 流必然满足。

代价：启动时多等 376 字节。对 4 Mbps 流是 0.75 ms，可忽略。

**运行期校验**：每包只查 `buf[0] == 0x47`（1 字节，够用）。不符则：

- 该包丢弃，`resyncs++`；
- 回到 SEARCHING，从当前位置往后逐字节找下一个同步点。

**不做的事情**：不校验 continuity_counter。原因：现场设备（编码器 / 摄像头）
的 CC 实现经常不规范，用它判失步会误杀正常流。CC 只用于诊断计数。

### 5.3 PS 同步算法

搜索 `00 00 01 BA`（`pack_header_start_code`）。

比 TS 简单，因为 4 字节固定模式误判率已经够低（1/2^32），且 MPEG-2 规范里
pack header 在每个 pack 起始位置必然出现。MPEG-1 兼容流同样有 pack header
（结构不同，但 startcode 相同），所以同一套搜索对两种流都成立。

**命中后**：从该处开始解析 pack header，再依次处理后续的
`system_header(0xBB)` / `PSM(0xBC)` / `PES(0xE0..0xEF, 0xC0..0xDF, 0xBD)`。

**失步判据**：连续 4 个字节不是 `00 00 01 xx` 的合法组合 → 回 SEARCHING。

### 5.4 PES 组装与帧边界

**TS 侧**（按 PID 分别累积）：

```
PUSI == 1  → 上一帧结束，开始新 PES
PUSI == 0  → 追加到当前 PES
```

边界判定完全依赖 `payload_unit_start_indicator`，**不依赖 PES_packet_length**
（现场很多编码器把视频 PES 的 length 填 0，表示"直到下一个 PUSI 为止"）。

**PS 侧**：PES 自带 `PES_packet_length`，按长度切；长度为 0 时同样退化为
"读到下一个 startcode 为止"。

**AUD 切分**：TS/PS 里一个 PES 理论上是一帧，但部分编码器会把多帧塞进一个 PES。
`split_video_by_aud = true` 时按 H.26x 的 AUD（`00 00 01 09`）再切一次。
**默认关闭** —— 大多数场景下 PES 边界就等于帧边界，多切一次反而引入风险
（AUD 在 SPS/PPS 之间出现时会把参数集切到独立帧）。

**参数集（SPS/PPS/VPS）**：随码流走，不单独提取。若第一个 PES 里带参数集，
会作为普通帧（`FrameFlag::config` 未置位，因为无法可靠区分"纯参数集帧"）吐出。
真正需要 extradata 的场景（PS 的 PSM 描述符）由 mux 侧的 `StreamConfig::extradata` 提供。

### 5.5 时间戳

- 单位 **90 kHz**，与 PTS/DTS 的 33 bit 表示一致；
- 编码格式（5 字节，大端）：

```
PTS only:        0010  PTS[32..30] 1  PTS[29..15] 1  PTS[14..0] 1
PTS + DTS:       0011  PTS[32..30] 1  PTS[29..15] 1  PTS[14..0] 1
                      0001  DTS[32..30] 1  DTS[29..15] 1  DTS[14..0] 1
```

- **33 bit 回绕**（约 26.5 小时一轮）：库内**不做**展开，原样交出。
  需要绝对时间的调用方用 `clockToMs()` 换算后自行处理回绕 —— 这是应用层语义，
  库不该替调用方决定"跨绕后是 +还是-"。
- `kNoTimestamp`（INT64_MIN）表示 PES 里没有该时间戳。

### 5.6 内存模型

**为什么做不到零拷贝**：一帧 ES 在 TS 里被切成 N 个 188 字节包，物理上分散在
buffer 的不同位置（中间还夹着其它 PID 的包）。要"零拷贝"交出，只能给
scatter/gather 视图（`span[]`），但下游（解码器、文件写入）几乎都要求连续内存。

所以：**每帧一次 `memcpy`，目标缓冲按流复用**。

```
每流一个 std::vector<uint8_t> frame_buf：
  vector::clear() + reserve(上次峰值), 追加各包 payload
  → 回调 span(frame_buf.data(), size)
  → 下一帧继续复用同一块
```

稳态下**不分配内存**（vector 容量只增不减，峰值由 `max_frame_bytes` 兜住）。

| 缓冲 | 数量 | 上限 | 说明 |
|---|---|---|---|
| `ByteQueue` | 1 | `max_buffered_bytes`（4 MiB） | 未成帧的输入 |
| `frame_buf` | 每流 1 | `max_frame_bytes`（4 MiB） | 单帧组装 |
| `PMT/PAT 表` | 1 | 无（结构固定，几百字节） | |
| `Muxer` 输出块 | 1 | 64 KiB（PS） / 188*n（TS） | |
| `EsSplitter` 尾巴 | 1 | **3 字节** | 跨块起始码 |
| `EsSplitter` 帧缓冲 | 1 | `max_frame_bytes`（1 MiB） | 仅在 explicit_length 模式缓冲整帧 |

**总内存上界**：`4 MiB + 流数 × 4 MiB`。4 路流的典型场景约 20 MiB，
嵌入式板卡可接受。需要更紧可以调小 `max_frame_bytes`（1080p IDR 实测 < 1 MiB）。

### 5.7 线程模型

**单线程，回调同步**。不做内部线程、不做内部队列。

理由：
- 容器解析是纯计算，不涉及 IO，没有异步的理由；
- 引入线程就要引入队列、锁、生命周期管理，还会让"回调里能否重入"变成复杂问题；
- 调用方如果需要在别的线程消费，自己在回调里 push 到自己的队列即可 ——
  **这个决定本该由调用方做**。

**结论**：同一 `Demuxer` / `Muxer` 对象的所有方法必须在同一线程调用（非线程安全）。
不同对象之间无共享状态，可以各线程独立使用。

### 5.8 输出形态

| codec | 输入（mux）/ 输出（demux）形态 |
|---|---|
| H.264 / H.265 / H.266 | **AnnexB**（`00 00 00 01` 或 `00 00 01` 起始码） |
| AAC | 由 `StreamInfo::adts` / `StreamConfig::add_adts` 决定是否带 ADTS 头 |
| G.711 / G.722 / G.729 / OPUS | 裸帧，无容器头 |
| MP3 | 裸帧（不带 ID3） |

**不做转封装**：demux 吐出的就是容器里的原样字节，不补也不去头部。
唯一例外是 `add_adts = true` 时 mux 会**加** ADTS 头（因为 TS 规范要求 AAC 带 ADTS）。

### 5.9 mux 的非整帧输入：EsSplitter

**问题**：从设备拿到的 H.264 裸流是 TCP/文件读出来的**任意切片**——不落在帧边界，
甚至起始码会被切在两次读之间（`... 00 00 | 00 01 65 ...`）。

**做法**：`EsSplitter` 内部只维护**最多 3 字节尾巴** + 一个"当前帧已累积长度"，
不缓冲整帧。

```
feed(data):
  1. 把上次的 3 字节尾巴拼到当前块前面（拼成一个临时 span）
  2. 逐字节扫 00 00 01 / 00 00 00 01
  3. 每遇到起始码：
       - 如果当前帧非空 → 上一帧结束，回调出去
       - 开始新帧
  4. 块尾不足 4 字节的部分留下当尾巴
```

**为什么不用缓冲整帧**：

PES 头里的 `PES_packet_length` **可以填 0**（含义是"长度不定，到下一个起始码为止"）。
所以封包可以**收一块、封一块、发一块**，内存只有几 KB。

代价：`length = 0` 的 PES 对某些严格解析器不友好（ffmpeg / GB28181 平台都接受）。
需要严格长度的场景，可以在 `MuxerConfig` 里开 `pes_explicit_length`——那时
`EsSplitter` 要先攒到"下一帧起始码出现"才知道上一帧多长，最坏缓冲一整帧。

| 模式 | 内存 | 适用 |
|---|---|---|
| `pes_explicit_length = false`（默认） | 几 KB | 实时推流（GB28181） |
| `pes_explicit_length = true` | 最坏一整帧（~1 MiB） | 需要写文件、第三方解析器挑剔 |

**不做的事**：不判断哪个是 IDR。`EsSplitter` 只切边界，帧标志（key/config）
由调用方在 `write()` 时告知——因为"这是不是关键帧"需要看 slice_type，
那是解码器语义，容器层不该猜。

#### "非开头输入"的四种情况

"不分帧"和"不是开头"是两回事，要分开说：

| 场景 | 可行性 | 处理 |
|---|---|---|
| **demux PS，从中间开始** | ✅ 立即自同步 | 扫 `00 00 01 BA` / `E0` |
| **demux TS，从中间开始** | ⚠️ 有延迟 | 先按 3×0x47 对齐 188 包，再**等下一个 PAT/PMT**（100~500ms），此间返回 `waiting_psi` |
| **mux，从帧中间开始** | ⚠️ 丢残片 | 丢到第一个起始码，计入 `dropped_leading_bytes` |
| **mux，从帧边界但是 P 帧** | ⚠️ 首帧解不出 | PS/TS 结构正确，但解码器缺参考帧，要等下一个 IDR |

**TS 为什么必须等 PSI**：即使按 0x47 对齐了 188 包边界，也没人知道哪个 PID
是视频——必须读 PMT 的 `stream_type` + `elementary_PID` 映射。

**PS 为什么能立即自同步**：起始码**自解释**。`00 00 01 E0` 就是视频 PES，
不需要任何表。

（libmpeg 就是这个行为：PS 的 demuxer 有 `ps_sync_start_probe` 主动找同步点；
TS 的 demuxer 直接 `assert(0x47 == data[0])`，要求调用方保证对齐。）

**封装侧要保证首帧可解，只能由调用方从 IDR 开始喂**——库判断不了"这是不是
关键帧"（那要看 slice_type，属于解码器语义）。

### 5.10 错误处理：四级分类

错误**不能一视同仁**——单包 CRC 错和内存分配失败，处置方式完全不同。

| 级别 | 错误码 | 是否中断 | 库做什么 | 调用方做什么 |
|---|---|---|---|---|
| **L1 调用方错误** | `invalid_argument` / `stream_not_found` / `not_configured` | 否 | 立即返回，**不改状态** | 修参数 |
| **L2 数据错误** | `malformed` / `unsupported_codec` | 否 | 丢掉该单元，计数 | 可忽略，看统计 |
| **L3 失步** | `sync_lost` / `buffer_overflow` / `waiting_psi` | 否 | 自行处置（回搜索态/丢最旧/等 PSI） | 继续 feed |
| **L4 致命** | `out_of_memory` / `internal_error` | **是** | 对象进 failed 状态 | **必须 reset()** |

**L4 的处理是设计重点**：

```
遇到 L4
  → 对象进入 failed 状态
  → 后续所有 feed/write/flush 立刻返回同一个错误码
  → 调用 reset() 才能恢复（清缓冲、状态机、统计，保留配置和回调）
```

为什么不用"自动重置"：那会让调用方不知道发生过什么。
为什么不用"直接报废"：一次 `bad_alloc` 不该让整条链路重建对象。

**`waiting_psi` 的特殊性**：它不是错误，而是"TS 已对齐包边界，但还没收到
PAT/PMT，不知道哪个 PID 是视频"。调用方看到它**什么都不用做，继续喂**。
如果 500ms 后还是它，才说明流有问题。

**一条铁律：所有"丢了多少"都必须在 `stats()` 里可见。**

```cpp
// 错的：静默跳过，调用方以为一切正常
default: return;

// 对的
default:
    m_stats.unknown_stream_ids++;
    return;
```

出问题时，"有计数"和"没计数"的区别就是"能查"和"只能猜"。

### 5.11 回调契约

四条契约，每条都对应我们踩过的坑。

#### ① 回调参数（`span`）的生命周期

`frame` / `payload` 指向**库内部复用的缓冲**，回调返回后立即失效。

**为什么复用**：25fps × 100 路 = 2500 次/秒，每帧都新分配太贵。

**契约**：要保留（放进队列异步处理）**必须自行拷贝**。

> 这是最典型的坑：症状是"对端收到垃圾"，排查很久才发现是缓冲被下一帧覆盖。

#### ② 回调对象（`std::function`）的生命周期

**库持有 `std::function` 的拷贝**，直到对象销毁。

**所以 lambda 捕获的东西必须活到对象销毁。**

```cpp
// 反例（会崩）
void setup() {
    int counter = 0;
    auto d = Demuxer::create(cfg, [&counter](auto f, ...) {
        counter++;            // setup() 返回后 counter 已死
    }, ec);
}

// 正确做法
auto state = std::make_shared<MyState>();       // 1. 捕获 shared_ptr
auto d = Demuxer::create(cfg, [state](auto f, ...) {
    state->counter++;
}, ec);
```

**要解绑**（owner 先死）：`setHandler(nullptr)`。

#### ③ 回调里不能调用本对象

```cpp
splitter->feed(data, [&](auto frame) {
    splitter->feed(more, ...);   // ← 禁止
});
```

`feed` 内部有"处理到哪个字节"的游标，重入会让游标错乱。

**可以调用别的对象**（比如拿到帧后 `muxer->write()`）——那是正常用法。

#### ④ 析构不回调

`~Demuxer()` / `~Muxer()` **不触发任何回调**，也不隐式 flush。

**理由**：析构期间触发回调，调用方可能在回调里访问正在析构的对象
（引用计数、成员变量），必崩。

**正确做法**：

```cpp
d->flush();       // 显式交出残留帧
d.reset();        // 再销毁
```

> 这一条是血泪教训：我们上一版的 `on_close` 里做清理，清理过程中对象
> 引用计数归零自析构，`close()` 还在栈上跑，直接 SIGSEGV。

## 6. 实现要点

### 6.1 TS 解封装

```
PID 0x0000 → PAT  → 每个 program: program_number + PMT_PID
PID = PMT_PID → PMT → 每路 ES: stream_type + elementary_PID + descriptors
PID = ES_PID  → PES 累积（按 PID 各一份）
PID 0x1FFF → NULL，丢弃
```

- `transport_scrambling_control != 0` → 该包丢弃（加密流不支持，计 `parse_errors`）
- `transport_error_indicator == 1` → 丢弃该包（上游已判定损坏）
- `adaptation_field_control`：`10` 仅 adaptation（PCR/填充），`11` 两者都有
- **PCR**：从 adaptation field 里取 `program_clock_reference_base`，仅用于
  诊断（可算抖动）；v1 不基于 PCR 做时间校正
- **PMT 版本变化**：`version_number` 变化时重解析，新增流触发 `on_stream`

#### 实现时踩到的三个坑（都记在这，省得下次再犯）

**1) PMT 的 `program_info_length` 在偏移 10，不是 12。**

```
[0]table_id [1..2]section_length [3..4]program_number [5]version
[6]section_number [7]last_section_number [8..9]PCR_PID [10..11]program_info_length
[12...] ES 循环（每项 stream_type + elementary_PID + ES_info_length + info）
[末 4 字节] CRC32
```

早先按"跳过 12 字节头"从偏移 12 读 `program_info_length`，读到的其实是
第一条 ES 的 `stream_type` 和 PID 高位。后果很隐蔽：**同步上了、状态机进了
`ready`、但 `m_streams` 永远是空的**，表现为"TS 一个包都没吐"，
而 `resyncs` / `parse_errors` 全是 0 —— 统计健康，数据为空。

判据要反过来看：**`stats` 全 0 且帧数 0，说明不是数据坏，是表没读对。**

**2) PES 收尾不能只靠下一条 PUSI。**

`PES_packet_length != 0` 时，收满 `6 + length` 就该交出去。否则：
- 最后一条 PES 要等 `flush()` 才出（延迟一帧）
- TS 的最后一包会用 adaptation field 填到 188，payload 尾部带 stuffing，
  直接取到包尾会把垃圾塞进 ES

所以两条路径都要有：**长度可知 → 收满即出；长度 0（大帧，>64 KiB）→ 等下一个 PUSI**。

**3) 一条 PES 里可能有几十个 ADTS 帧。**

我们自己的复用器是"一帧一 PES"，但 ffmpeg / 摄像机常常攒几十个 AAC 帧
发一条 PES 省包头。按 PES 边界整段交出，调用方拿到的是"一坨 ADTS"。

处理：`codec == aac` 时按 ADTS 的 `frame_length` 拆成单帧，
PTS 按 `1024 * 90000 / sample_rate` 递增（采样率从 `sampling_frequency_index` 取）。
拆不出来（首字节不是 `0xFF 0xF?`）就原样透传，绝不吞数据。

实测对照：ffmpeg 打的 TS 里 88 个 AAC 帧挤在 6 条 PES 里，拆分后正好 88 帧，
与源文件帧数一致。


### 6.2 PS 解封装

```
00 00 01 BA → pack_header（MPEG-2 或 MPEG-1，靠 marker bit 区分）
00 00 01 BB → system_header（跳过）
00 00 01 BC → PSM（拿 stream_type 映射，用于确定 codec）
00 00 01 BD → private_stream_1（G.711 等，靠 PSM 或启发式）
00 00 01 E0..EF → 视频 PES
00 00 01 C0..DF → 音频 PES
```

**MPEG-2 / MPEG-1 pack header 区分**：MPEG-2 的第 4 字节高 2 位是 `01`，
MPEG-1 是 `0010`（SCR 直接编码）。
按第 5 个字节（`b[4]`）判定：`(b[4] >> 6) == 0b01` 为 MPEG-2，
`(b[4] >> 4) == 0b0010` 为 MPEG-1。两者在 bit5 上不同，不会歧义。

**codec 判定顺序**：PSM 优先 → stream_id 范围推断（0xE0 视频 / 0xC0 音频）→
探测码流首字节（H.264 的 `00 00 00 01 67`）。三者都没有就报 `unknown`。

### 6.3 TS 封装

```
每帧 PES → 首包 PUSI=1 + 含 PES 头 → 后续包 184 字节填满
PAT/PMT: 按 psi_period_ms 周期重发（默认 100 ms）
PCR:     按 pcr_period_ms 在 PCR_PID 的包上插 adaptation field（默认 40 ms）
```

**CRC32**：MPEG-2 多项式 `0x04C11DB7`，初值 `0xFFFFFFFF`，
**不反转输入/输出，不做最终异或**。这是 PSI 段的标准，与 zlib 的 CRC32 不同。

**打包细节**：
- 包长固定 188；末尾不足时用 adaptation field 的 stuffing 补齐
- `continuity_counter` 每包 +1（仅含 payload 的包），回绕到 0
- 一帧跨多包时，只有首包 PUSI=1

### 6.4 PS 封装

```
pack_header (0xBA) + [system_header (0xBB)] + [PSM (0xBC)] + PES...
```

- `program_mux_rate` 单位是 **50 bytes/s**，按 `ps_pack_bytes` 与预估码率算
- `SCR_base` **直接取最近一帧的 dts**（SCR/PCR 的 base 部分单位就是 90 kHz，33 位 = `dts & 0x1FFFFFFFF`），`SCR_extension = 0`。
  27 MHz 由 `base × 300 + extension` 构成，extension 全 0 时精度即 90 kHz —— 对 PS 的用途（缓冲模型）足够
- 首帧输出 system_header + PSM（PSM 里带 codec 映射，让对端能直接识别）
- 之后每 `ps_pack_bytes` 内的 PES 共用一个 pack header

## 7. 测试策略

### 7.1 单元测试（自带，无外部依赖）

| 用例 | 内容 |
|---|---|
| `sniff` | PS / TS / 垃圾数据的识别；不足 564 字节的边界情况 |
| TS 同步 | 前缀插 N 个垃圾字节仍能同步；前缀恰好含 0x47 的对抗样本 |
| 切分不变性 | **同一段流按 1/7/188/1000/全部 五种切分喂入，输出帧序列必须逐字节相同** |
| 失步恢复 | 中途挖掉 500 字节，能重新同步且 `resyncs > 0` |
| 溢出 | 只喂不消费，验证 `buffer_overflow` 与恢复 |
| 时间戳 | 33 bit 编解码；回绕不 panic |
| 往返 | `mux → demux`，帧与 pts 逐条相等 |

**切分不变性是最重要的用例** —— 它直接把"非整帧输入"这个卖点变成可验证的断言。

### 7.2 互操作测试（有环境时跑）

| 方向 | 工具 | 判据 |
|---|---|---|
| ffmpeg 产出 PS/TS → mpegmech demux | `ffmpeg -f lavfi -i testsrc` | 帧数、关键帧位置、首个 pts 一致 |
| mpegmech mux → ffmpeg 解读 | `ffprobe` | 识别出正确 codec / 分辨率 / 帧率，能完整解码无报错 |
| 与 libmpeg 交叉 | 同一段流分别过两个库 | 帧数与 pts 序列一致 |

### 7.3 现场验收

1. 板端从 ZLMediaKit 拉一路 PS 流，按 `recv()` 原始块喂 `feed()`；
2. 统计 `resyncs == 0`、`parse_errors == 0`、帧率与摄像头标称一致；
3. 连续跑 24 h，内存曲线平稳（对齐 ipms 那次泄漏事故的验收口径）。

## 8. 风险与未决项

| # | 项 | 说明 | 处置 |
|---|---|---|---|
| R1 | **参考实现的许可证** | 若参考 libmpeg 的解析逻辑，其 MIT 许可证要求保留版权声明；逐行照抄会污染本项目授权 | 只按 **ISO/IEC 13818-1 标准**实现，不复制代码；若确需借用，在 `NOTICE` 里逐文件声明 |

| R5 | 裸 ES 拆帧缺失 | mux 需要整帧，调用方若只有字节流会卡住 | v2 补 `EsSplitter`（AnnexB 起始码 + ADTS 长度） |
| R6 | 帧率/时间基信息 | 本库不解析 SPS/VUI，不推算帧率 | 由调用方提供，或下游解码器提供 |
